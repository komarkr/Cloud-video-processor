# Сценарій демонстрації та захисту проєкту: Cloud Video Processor

Цей документ містить покроковий сценарій для успішної демонстрації та захисту курсового проєкту **Cloud Video Processor (CVP)** перед екзаменаційною комісією / викладачем. Кожен крок містить точні команди, очікуваний результат та технічні пояснення внутрішніх механік системи.

---

## Підготовка перед демонстрацією (Запуск з нуля)

1. **Клонування або перехід у папку проєкту:**
   ```bash
   cd Cloud-video-processor
   ```

2. **Ініціалізація змінних середовища:**
   ```bash
   cp .env.example .env
   ```

3. **Збірка статичного фронтенду:**
   ```bash
   npm --prefix frontend run build
   ```

4. **Запуск усього стеку сервісів з 2 воркерами:**
   ```bash
   docker compose down -v
   docker compose up --build -d --scale worker=2
   ```

5. **Перевірка готовності контейнерів:**
   ```bash
   docker compose ps
   ```
   *Очікуваний стан:* сервіси `postgres`, `redis`, `api1`, `api2`, `dispatcher`, два екземпляри `worker`, `autoscaler`, `nginx` мають статус `Up` (сервіс `migrate` завершується зі статусом `Exited (0)` після застосування міграцій).

6. **Відкриття вебінтерфейсу:**
   - URL: **`https://localhost`**
   - *Примітка щодо SSL:* сертифікат видано для `localhost` через `mkcert`. Якщо браузер попереджає про самопідписаний сертифікат, оберіть «Продовжити (небезпечно)» або заздалегідь додайте кореневий сертифікат mkcert у систему (`mkcert -install` або `certutil -user -addstore Root nginx\certs\localhost.pem`).

## 🎯 Сценарій демонстрації (10 кроків)

### Крок 1. Балансування навантаження та відмовостійкість (КТ1)

**Мета:** Продемонструвати розподіл запитів між двома незалежними екземплярами API (`api1` та `api2`) за допомогою Nginx (`least_conn`) та безперебійну роботу в разі падіння одного сервера.

1. **Перевірка розподілу запитів (`X-Served-By`):**
   Виконайте кілька послідовних запитів через термінал:
   ```bash
   curl -k -s -D - https://localhost/api/health -o /dev/null | grep -i "x-served-by"
   curl -k -s -D - https://localhost/api/health -o /dev/null | grep -i "x-served-by"
   ```
   *Очікуваний результат:* Відповіді містять по черзі заголовки `X-Served-By: api1` та `X-Served-By: api2`.

2. **Симуляція аварії API-сервера:**
   Зупиніть контейнер `api1`:
   ```bash
   docker compose stop api1
   ```
   Повторіть запит до API або оновіть сторінку в браузері:
   ```bash
   curl -k -s https://localhost/api/health
   ```
   *Очікуваний результат:* Система повертає `{"status":"ok","server_id":"api2"}` без жодних затримок або помилок 502. Директива `proxy_next_upstream` у Nginx автоматично перенаправляє запити на живий екземпляр.

3. **Відновлення сервера:**
   ```bash
   docker compose start api1
   ```

### Крок 2. Авторизація, сесії та захист від брутфорсу

**Мета:** Показати безпечну реєстрацію користувачів, автентифікацію через `HttpOnly` JWT cookie та обмеження частоти запитів (`limit_req`).

1. **Реєстрація та вхід користувача:**
   - На сторінці `https://localhost` перейдіть на вкладку **«Реєстрація»**.
   - Створіть обліковий запис: `student@example.com` / `Password123!`.
   - Система автоматично виконає вхід та перенаправить до робочого кабінету.
2. **Перевірка безпеки Cookie в браузері (DevTools):**
   - Натисніть `F12` → вкладка **Application / Storage** → **Cookies** → `https://localhost`.
   - Знайдіть cookie `access_token`:
     - Прапорець **HttpOnly** встановлено (токен недоступний через JavaScript `document.cookie`, захист від XSS).
     - Прапорець **Secure** встановлено (передається лише через захищене TLS-з'єднання).
     - Прапорець **SameSite=Lax** встановлено (захист від CSRF-атак).
3. **Демонстрація Rate Limiting (`limit_req` на `/api/auth/`):**
   Запустіть швидку серію запитів до ендпоінту авторизації:
   ```bash
   for i in {1..15}; do curl -k -s -o /dev/null -w "%{http_code}\n" -X POST https://localhost/api/auth/login -H "Content-Type: application/json" -d '{"email":"bad@ex.com","password":"bad"}'; done
   ```
   *Очікуваний результат:* Перші запити повертають `401 Unauthorized`, а наступні — `429 Too Many Requests` (спрацьовує `limit_req_zone $binary_remote_addr zone=auth_limit:10m rate=5r/s` у Nginx).

### Крок 3. Завантаження та валідація відео (п. 1)

**Мета:** Довести надійність вхідного контролю медіафайлів за допомогою `ffprobe`.

1. **Завантаження валідного відео:**
   - На сторінці «Нова задача» у блоці **«Готові тестові відео та логотип»** натисніть на будь-яке відео для завантаження на диск (наприклад, фрактал `fractal_universe_30s.mp4` або частинки `cyber_particles_20s.mp4`), або оберіть власний файл.
   - Оберіть операцію: **«Конвертація (MP4 / H.264 + AAC)»**.
   - Натисніть **«Створити задачу»**.
   - *Результат:* Задача успішно створена зі статусом `queued`. API не запускає обробку напряму, а залишає вибірку для координатора Dispatcher.
2. **Спроба завантажити пошкоджений файл або не-відео:**
   - Спробуйте завантажити текстовий файл, перейменований на `.mp4` (наприклад, `test.txt` → `test.mp4`).
   - *Результат:* Інтерфейс та API повертають помилку валідації `422 Unprocessable Content: Invalid file format: file is corrupt or not a recognized media file`. Некоректний файл негайно видаляється з диска.
3. **Перевірка обмеження тривалості (<= 120 с):**
   - При спробі завантаження відео тривалістю понад 120 с API повертає `422: Video duration (X s) exceeds maximum allowed 120 seconds`.
4. **Безпечні імена файлів (UUID-only):**
   - Перевірте каталог `/data/uploads` на хості/контейнері: усі збережені файли мають виключно назви формату `<uuid>_input.mp4`. Жодні клієнтські назви чи спроби path traversal не потрапляють у файлову систему.

### Крок 4. Операції обробки та відстеження прогресу через SSE (КТ2, КТ3)

**Мета:** Продемонструвати всі підтримувані типи обробки відео та реактивне оновлення прогресу в реальному часі.

1. **Підтримувані операції:**
   - **Конвертація:** H.264 / AAC швидкий профіль.
   - **Зміна роздільної здатності (Scale):** вибір `1080p`, `720p`, `480p`, `360p` з адаптивним підбором CRF.
   - **Водяний знак (Watermark):** накладання PNG-зображення з вибором позиції (правий нижній кут, центр тощо) та прозорості (opacity).
   - **Аудіо (Audio Extraction / Mute):** вилучення звукової доріжки у MP3 або повне приглушення відео без повторного перекодування відеопотоку (`-c:v copy -an`).
2. **Real-time SSE прогрес:**
   - Під час виконання задачі відкрийте вкладку **Network** у браузері.
   - Знайдіть запит `GET /api/tasks/{task_id}/events`.
   - *Пояснення комісії:* З'єднання працює за стандартом Server-Sent Events (SSE). Раз на секунду API зчитує з Redis поточний відсоток прогресу (`progress:{task_id}`), що записується координатором Dispatcher під час опитування воркера, та транслює в браузер (`data: {"status": "running", "progress": 45}`).
3. **Завантаження результату та вбудований перегляд:**
   - Після завершення обробки (`status: done`) Dispatcher завантажує вихідний файл у `/data/outputs/{task_id}_output.mp4`. У вебінтерфейсі з'являється кнопка **«Скачати»** та відеоплеєр `<video controls>` для попереднього перегляду безпосередньо на сторінці.

### Крок 5. Нова архітектура: Dispatcher, HTTP Push, Балансування та Відмовостійкість

**Мета:** Продемонструвати мережевий розподіл задач координатором Dispatcher, балансування між ізольованими HTTP-воркерами та стійкість до аварій.

1. **Журнал розподілу задач (Dispatcher Log) в Адмін-панелі:**
   - Увійдіть під адміністратором (`admin@example.com` / `admin_password_123`) і перейдіть у розділ **«⚡ Адмін-панель»**.
   - Знайдіть таблицю **«Журнал розподілу задач (Dispatcher Log)»**:
     - Фіксуються типи подій: `registered`, `dispatched`, `completed`, `requeued`, `worker_dead`.
     - Записи містять `task_id`, `worker_id` та додаткові корисні деталі (наприклад, номер спроби `attempt`, причину повернення в чергу тощо).
2. **Балансування навантаження (`least_loaded` / `round_robin`):**
   - Dispatcher обирає воркера з найменшою кількістю активних задач (`least_loaded`). Якщо всі воркери зайняті, задача безпечно чекає у статусі `queued` наступного циклу опитування.
3. **Демонстрація відмовостійкості (Worker Crash & Auto-Requeue):**
   - Запустіть важку задачу (наприклад, відео 30 с із водяним знаком).
   - Коли задача перейде у статус `running` на `worker-1`, зупиніть контейнер воркера:
     ```bash
     docker compose stop worker
     ```
   - Зачекайте кілька секунд. Координатор Dispatcher виявить, що воркер перестав відповідати (`3` невдалі опитування), позначає воркера `dead`, фіксує подію `worker_dead` і автоматично скидає задачу назад у статус `queued` зі збільшенням лічильника спроб (`attempt = 1`).
   - Запустіть воркер знову або запустіть новий:
     ```bash
     docker compose start worker
     ```
   - Воркер відновить реєстрацію, Dispatcher підхопить задачу з черги і завершить її успішно без втрати даних користувача!
4. **Підключення зовнішнього воркера поза Docker Compose:**
   - На будь-якому терміналі запустіть автономний воркер:
     ```bash
     export WORKER_ID=laptop-worker-external
     export WORKER_PORT=9005
     export WORKER_CAPACITY=1
     export WORKER_PUBLIC_URL=http://localhost:9005
     export DISPATCHER_URL=http://localhost:8100
     export WORKER_TOKEN=secret_worker_token_change_in_production
     uvicorn worker_server.main:app --port 9005
     ```
   - Воркер автоматично зареєструється у Dispatcher і негайно з'явиться у таблиці активних воркерів адмін-панелі.

### Крок 6. Скасування задачі (Cooperative Cancellation)

**Мета:** Показати механізм миттєвого та безпечного скасування задачі користувачем.

1. Завантажте відео та одразу натисніть червону кнопку **«Скасувати»**.
2. **Що відбувається під капотом:**
   - Клієнт викликає `POST /api/tasks/{id}/cancel`.
   - Якщо задача ще була у черзі (`queued`), вона миттєво переходить у статус `cancelled`.
   - Якщо задача вже виконувалася (`running`), встановлюється прапорець скасування `cancel:{task_id}` у Redis, а Dispatcher надсилає виклик `POST /tasks/{task_id}/cancel` безпосередньо на воркер-сервер.
   - Воркер виставляє прапорець `threading.Event`, перериває процес FFmpeg (`SIGTERM`, через 5 с `SIGKILL`), очищає локальні файли задачі, повертає статус `cancelled` і звільняє слот для наступних задач.

### Крок 7. Черга, ліміти користувача та розрахунок ETA (п. 6)

**Мета:** Продемонструвати чергування задач, розрахунок орієнтовного часу очікування та обмеження активних задач.

1. **Розрахунок ETA:**
   - Надішліть кілька задач поспіль.
   - Задачі, що чекають черги, отримують бейдж: `У черзі: місце 2, приблизно 25 с`.
   - *Формула розрахунку комісії:*
     $$\text{ETA} = \frac{\text{тривалість попередніх задач у черзі} + \text{залишок виконання поточних}}{\text{середня швидкість системи} \times \max(\text{сумарна місткість воркерів}, 1)}$$
2. **Ліміт активних задач (максимум 5):**
   - Створіть 5 активних задач від одного користувача.
   - При спробі створити 6-ту задачу клієнт отримує помилку `429 Too Many Requests: Active tasks limit exceeded (maximum 5 active tasks allowed)`.

### Крок 8. Heartbeat та динамічне автомасштабування (п. 7)

**Мета:** Довести здатність кластера самостійно адаптуватися до пікових навантажень.

1. **Heartbeat воркерів у Redis:**
   Виконайте команду перегляду heartbeat-ключів:
   ```bash
   docker compose exec redis redis-cli keys "hb:*"
   docker compose exec redis redis-cli hgetall "hb:worker"
   ```
   *Очікуваний результат:* Повертаються поля `cpu`, `ram`, `capacity`, `active_tasks`, `timestamp`. Ключ має TTL 10 секунд. Якщо воркер упаде, ключ зникає автоматично.
2. **Створення навантаження для Autoscaler:**
   - На сторінці «Мої задачі» натисніть кнопку **«🔥 Стрес-тест (навантаження)»** або запустіть скрипт:
     ```bash
     python scripts/trigger_cluster_load.py
     ```
   - За умов `queued > n * PER_WORKER`, сервіс `autoscaler` фіксує перевантаження і через Docker SDK запускає додаткові контейнери HTTP-воркерів (`scale_up`) аж до максимуму (`MAX_WORKERS=4`). Нові воркери запускаються без монтування тому `/data`, самореєструються в Dispatcher і негайно підхоплюють задачі.
3. **Scale down при простої:**
   - Після завершення задач у черзі та спливу часу простою (`IDLE_FOR=30s`) додаткові контейнери воркерів автоматично зупиняються та видаляються. Подія фіксується у списку `autoscaler:events` та відображається в адмін-панелі.

### Крок 9. Адмін-панель кластера (`/admin`) (КТ4)

**Мета:** Продемонструвати повноцінний моніторинг інфраструктури та централізоване керування.

1. **Вхід під адміністратором:**
   - Увійдіть з адмін-даними: `admin@example.com` / `admin_password_123`.
   - У верхній панелі навігації з'явиться кнопка **«⚡ Адмін-панель»** (недоступна звичайним користувачам).
2. **Огляд метрик у реальному часі:**
   - Сторінка автоматично оновлює дані раз на 3 секунди.
   - **Картки:** кількість задач за статусами (`queued`, `running`, `done`, `failed`, `cancelled`), довжина черги, загальна кількість задач.
   - **Таблиця воркерів:** список усіх активних воркерів із живими індикаторами завантаження CPU та RAM, URL-адресою, місткістю та міткою «востаннє бачили».
   - **Журнал Dispatcher Log:** детальна хронологія передачі файлів, завершення та відновлення задач.
   - **Журнал масштабування:** хронологічний аудит подій автомасштабування (`scale_up`, `scale_down`).
   - **Останні 50 задач:** детальна таблиця задач усіх користувачів кластера з можливістю для адміністратора примусово скасувати будь-яку активну задачу.

### Крок 10. Фонове очищення застарілих задач (Cleanup)

**Мета:** Показати механізм захисту дискового простору від переповнення.

1. **Як працює очищення:**
   - Кожна завершена задача отримує часову мітку `expires_at = finished_at + RESULT_LIFETIME_HOURS` (за замовчуванням 24 години).
   - Фонове завдання кожні 10 хвилин (або за викликом кнопки очищення в адмін-панелі) знаходить прострочені задачі.
   - Автоматично видаляються всі пов'язані файли (`input_file`, `output_file`, логотипи, логи з `/data/logs/`) та очищаються записи у PostgreSQL і ключі Redis.
2. **Демонстрація через API:**
   ```bash
   curl -k -X POST https://localhost/api/admin/cleanup --cookie "access_token=..."
   ```
   *Результат:* `{"status":"ok","message":"Successfully purged X expired tasks.","purged_count":X}`.

## 💡 Типові запитання комісії та відповіді

1. **Чому було обрано архітектуру HTTP Push через Dispatcher замість брокера черг Celery/Redis pull?**
   - *Відповідь:* У pull-моделі (Celery) усі воркери зобов'язані мати прямий мережевий доступ до брокера черги (Redis), бази даних та спільної файлової системи (Docker volume або NFS). Це унеможливлює винесення воркерів на зовнішні комп'ютери чи окремі хмарні сервери без організації складних мережевих дисків і порушує принципи безпеки (воркери мають паролі до БД).
   У новій архітектурі **воркер — це повністю ізольований stateless HTTP-сервер**. Йому не потрібні БД, Redis чи спільний том. Dispatcher централізовано володіє картиною всього кластера, відправляє задачі разом із файлами через HTTP streaming, контролює навантаження кожного воркера індивідуально (`least_loaded`) та гарантує надійність (автоматичний перезапуск на іншому воркері при падінні поточного).

2. **Як забезпечується ідемпотентність ендпоінту `POST /execute` на воркері?**
   - *Відповідь:* Якщо Dispatcher через тимчасовий збій мережі або повторну відправку надсилає задачу з уже відомим `task_id`, воркер не запускає повторний процес FFmpeg, а повертає `200 OK` з поточним станом та прогресом існуючої задачі.

3. **Як працює самореєстрація та heartbeat воркерів у Dispatcher?**
   - *Відповідь:* При запуску воркер у фоновому циклі надсилає `POST /internal/workers/register` на Dispatcher (передаючи свій `worker_id`, `url` та `capacity`), повторюючи запити кожні 10 секунд (heartbeat). При штатному завершенні роботи надсилається `POST /internal/workers/deregister`. Крім того, Dispatcher регулярно пінгує ендпоінт `/status` кожного воркера; якщо воркер не відповідає 3 рази поспіль, Dispatcher позначає його як `dead` і повертає його задачі в чергу `queued`.

4. **Як забезпечується робота без втрати станів (Stateless backend)?**
   - *Відповідь:* Обидва API-сервери (`api1` і `api2`) не зберігають сесій у локальній пам'яті контейнера. JWT-токен валідується за спільним секретним ключем, стан задач зберігається у PostgreSQL, а оперативний прогрес — у Redis. Будь-який запит клієнта може бути прозоро опрацьований будь-яким API-сервером через Nginx.

5. **Як захищена система від виконання шкідливого коду у файлах відео?**
   - *Відповідь:*
     1. Медіафайли проходять ретельну перевірку `ffprobe` перед постановкою в чергу;
     2. Усі виклики FFmpeg/ffprobe використовують аргументи у вигляді списку без shell (`shell=False`);
     3. Додано прапорець `-protocol_whitelist file`, який забороняє FFmpeg відкривати мережеві сокети або сторонні протоколи;
     4. Файли зберігаються на диску виключно під UUID-іменами з валідованими розширеннями;
     5. Взаємодія Dispatcher та Worker захищена токеном `X-Worker-Token`.
